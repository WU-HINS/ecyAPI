# 100 万张 / 极低内存 / 本地云端混合：设计稿

目标：**100 万张图**、**极低内存**、**本地+云端混合**、**原图不 302 暴露**、**自动方向**。

## 先看现状的内存账单（实测，不是估算）

```
当前索引每条 321 字节  →  100 万条 ≈ 306 MB   ← 直接否掉
```

（测法：`TestIndexMemoryPerEntry` 建 2 万条，量 HeapAlloc 差值，再线性外推。）

所以第一件事不是接远端，而是**换索引结构**。

## 核心设计：两级索引（内存只放「目录」，条目按需映射）

```
┌─────────────────────────────┐
│ 目录表（常驻内存）            │  2000 个分类 × ~64B ≈ 128 KB
│ name / count / source / off  │
└──────────────┬──────────────┘
               │ 按需 mmap（LRU 保留最近 30~50 个分类）
        ┌──────▼──────────────────────────────┐
        │ 分类条目数组（mmap，24B/条）          │  单个 500 条 = 12 KB
        │ hash64 | arenaOff | size | mtime | ori │
        └──────┬──────────────────────────────┘
               │ 偏移
        ┌──────▼──────────────┐
        │ 路径 arena（mmap）    │  平均 70B/条 → 70 MB 落盘，按页调入
        └─────────────────────┘
```

关键点：**内存里只常驻「分类表 + 最近访问的分类数组」**，100 万条的大部分永远在页缓存里、
需要时才由内核按页调入（可回收，不占堆）。

| 结构 | 100 万条规模 | 常驻内存 |
| --- | --- | --- |
| 分类表 | 2000 个分类 | ~0.13 MB |
| 热分类数组（LRU 50 个 × 500 条 × 24B） | — | ~0.6 MB |
| 路径 arena（mmap，按页命中） | 70 MB 落盘 | 热页几十 MB，可回收 |
| 运行时/连接/缓存 | — | ~25–35 MB |
| **合计 RSS 目标** | | **60–90 MB**（含页缓存）<br>**堆 < 40 MB** |

对比：老结构 306 MB 堆，且随图片数线性涨。

## 访问路径（全部是「先查分类 → 再按需读该分类」）

| 接口 | 需要的数据 | 代价 |
| --- | --- | --- |
| `/json?cat` | 该分类数组 + arena | 2 次 mmap 读取 |
| `/img?category=x` | 该分类数组（分页） | 顺序读，可流式 |
| `/@img` | 分类表（含权重） → 选中分类的数组 | 1 次随机 + 1 次定位 |
| `/pic/...` | 只查「该文件是否存在」→ 直接出流 | 一次 hash 命中 |

没有任何路径需要遍历 100 万条。

## 自动方向（不能靠扫全量）

100 万张远端图不可能在索引期逐张解码。策略：**惰性判定 + 持久化**

1. 记录里 `ori` 2 bit：0=未知、1=横、2=竖、3=方
2. 任一图片被真正取用（出图或生成缩略图）时，顺手解析文件头（几十字节）→ 写回该 bit
3. 查询带方向时：`ori` 已知的按需过滤；未知的视为「可满足任意方向」，并优先被选中去判定
4. 热图很快全部判定完；冷图永远不判定，也就不花任何代价

## 本地 + 云端混合（**图片级**，不是缩略图级）

两边存的是**原图**：一批图在本地盘，另一批在云端，同一个分类里也可能一半一半。
索引里每条记录带 1 bit 标明该文件在哪，请求时逐文件分流。

### 记录结构（28 字节，mmap 定长）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `hash` | u64 | 文件名 hash，用于二分查找 |
| `off` | u32 | 路径 arena 偏移 |
| `size` | u32 | 字节数（>4GB 走 side table） |
| `mtime` | u32 | 修改时间（秒，2020 起算） |
| `lastUse` | u32 | 最近访问（分钟粒度），分层淘汰用 |
| `oriFlags` | u8 | bit0-1 方向，**bit2 = 远端**，bit3 = 回迁中 |
| `pad` | u8 | 对齐 |

100 万条 = 28 MB 落盘，mmap 按页调入。

### 命名空间：本地与云端**不混在同一个分类**

一个分类要么全在本地、要么全在云端；云端整体挂在 `/@web/*` 下，
和本地分类的 URL 空间完全分开。

```
本地
  /{分类}                 → 302 到本域 /pic/{分类}/xxx      （随机一张）
  /pic/{分类}/{文件}       → sendfile（本地原图）
  /img?category={分类}     → 图库页
  /json?{分类}             → JSON
  /@img                   → 全部本地分类随机

云端（/@web 前缀）
  /@web/{分类}             → 302 到本域 /@web/pic/{分类}/xxx
  /@web/pic/{分类}/{文件}  → 代理流式转发（不暴露后端地址）
  /@web/img?category={分类}→ 云端图库页
  /@web/json?{分类}        → 云端 JSON
  /@web                    → 全部云端分类随机
```

注意：`/@web/pic/{分类}/{文件}` 是**本域**路径，302 只在本域跳转，
用户永远看不到 S3/OpenList 的地址与签名。

### 请求时的分流（分类级，不逐文件）

```
GET /pic/{分类}/{文件}       → 只查本地索引 → sendfile / 404
GET /@web/pic/{分类}/{文件}  → 只查云端索引 → 代理流式 / 404
```

- 两边索引各自独立（本地表 / 云端表），同名分类互不影响
- 因为不混，就不需要「逐文件判断在哪儿」，路由天然分离，热路径更短
- `oriFlags` 的 bit2 因此可以省掉（保留给「回迁中」状态用）

### 本地与云端同名分类怎么办

启动时检测：若某个分类同时存在于两端，**本地优先**，云端的同名分类在 `/@web` 下照常可用，
但图库与随机接口会各自独立列出（不会合并计数），日志里提示一次。

### 谁决定哪张图放哪

1. **手工放置**（默认）：本地目录 → 本地；`ECY_REMOTE_*` 描述的云端根 → 远端
2. **容量上限自动分层**：本地设 `ECY_LOCAL_MAX_BYTES`，超了按 `lastUse` 冷→热淘汰到云端
   （上传 + 删本地 + 置 bit2），后台低优先级执行
3. **热回迁**：N 天内访问 ≥ K 次 → 后台从云端拉回本地（promotion）

> `lastUse` 不在请求路径写盘：内存累加，30–60 秒批量回写一次。

### 容量账

| 指标 | 数值 |
| --- | --- |
| 总图片 | 100 万 × 2 MB ≈ 2 TB（全在云端） |
| 本地盘 | 100–300 GB（5%–15% 热图） |
| 本地命中率目标 | 80%–95% |
| 本地命中耗时 | sendfile，与现在一致 |
| 远端命中耗时 | 一次 RTT + 流式传输（不落盘） |

## 不 302 之后，带宽怎么办

原图全部经源站转发，所以必须靠缓存摊销：

| 层 | 策略 |
| --- | --- |
| CDN | `/pic/...` 已有 `public, max-age=604800` + ETag → 7 天，命中后不回源 |
| 源站 | 可选本地热缓存（LRU），命中直接 sendfile |
| 未命中 | 代理流式转发（不落盘） |

实测口径：首次访问走一次远端，之后 7 天由 CDN 承接。

## 失败模式与对策

| 风险 | 对策 |
| --- | --- |
| 远端 LIST 100 万条很慢（分页 1000/页 = 1000 次请求） | 后台增量刷新：只拉「顶层目录的 mtime」，变了才重扫该子树 |
| 远端超时/限流 | 分类级熔断 + 指数退避；该分类降级为「暂不可用」，不影响其它分类 |
| 代理被打满 | 并发闸门（复用现有 memguard 压力模型）+ 每 IP 限速 |
| mmap 文件损坏 | 索引文件带 magic+版本+crC32，坏则整份重建（与快照同思路） |
| 冷启动 100 万条 LIST | 先出「分类骨架」，条目按需填充（渐进式可用，复用现有 progressive 逻辑） |

## 里程碑 1 实测（已达成）

| 目标 | 设定 | 实测（100 万条） |
| --- | --- | --- |
| 落盘大小 | ≤30 MB | **41.1 MB**（43 B/条：28 B 记录 + 平均 17 B 路径） |
| 常驻堆 | ≤40 MB | **0.1 MB**（mmap 不计入堆） |
| 随机查询 | p50 < 50 µs | **0.8 µs/次**（20 万次 161 ms） |
| 构建耗时 | ≤5 s | **0.71 s** |

结论：索引文件大小略超预期（路径比预估长），但**它是落盘 + mmap 的，不进堆**；
真正影响内存的是「分类表 + 热分类切片」，实测堆占用 0.1 MB 级别。查询比目标快 60 倍。

## 里程碑

| # | 内容 | 交付物 |
| --- | --- | --- |
| 1 | 紧凑索引（分类表 + 24B 记录 + arena + mmap） | `internal/index`，含 100 万条压测（内存/查询延迟） |
| 2 | store 切到新索引（本地目录源） | 行为不变，内存从 306 MB → <40 MB |
| 3 | remote 源（WebDAV/S3 listing → 分类表 + 条目） | 索引只存元数据，不落原图 |
| 4 | `/pic` 混合分流 + 代理流式（禁 302） | 本地 sendfile / 远端 io.Copy 直通 |
| 5 | 惰性方向判定 + 持久化 | `ori` 位回写，热图自动分类 |
| 6 | 缩略图 LRU（容量上限 + 冷热淘汰） | 磁盘可控 |

## 与当前实现的关系

- 现有 `store` 的**扫描/发布/快照/内存控制**逻辑保留，替换的是「内存里怎么放条目」
- `ECY_DATA_DIR` 语义扩展为「本地源」；新增 `ECY_REMOTE_*` 描述云端源
- 单机 100 万条时，目标 RSS 60–90 MB（含页缓存），堆 <40 MB
