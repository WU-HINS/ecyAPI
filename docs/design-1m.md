# 100 万张 / 极低内存 / 本地云端混合：设计稿

目标：**100 万张图**、**极低内存**、**本地+云端混合**、**原图不 302 暴露**、**自动方向**。

## 先看现状的内存账单（实测，不是估算）

```
当前索引每条 321 字节  →  100 万条 ≈ 306 MB   ← 直接否掉
```

（测法：`TestIndexMemoryPerEntry` 建 2 万条，量 HeapAlloc 差值，再线性外推。）

所以第一件事不是接远端，而是**换索引结构**。

## 核心设计：两级索引（内存只放「目录」，条目按需映射）

```
┌─────────────────────────────┐
│ 目录表（常驻内存）            │  2000 个分类 × ~64B ≈ 128 KB
│ name / count / source / off  │
└──────────────┬──────────────┘
               │ 按需 mmap（LRU 保留最近 30~50 个分类）
        ┌──────▼──────────────────────────────┐
        │ 分类条目数组（mmap，24B/条）          │  单个 500 条 = 12 KB
        │ hash64 | arenaOff | size | mtime | ori │
        └──────┬──────────────────────────────┘
               │ 偏移
        ┌──────▼──────────────┐
        │ 路径 arena（mmap）    │  平均 70B/条 → 70 MB 落盘，按页调入
        └─────────────────────┘
```

关键点：**内存里只常驻「分类表 + 最近访问的分类数组」**，100 万条的大部分永远在页缓存里、
需要时才由内核按页调入（可回收，不占堆）。

| 结构 | 100 万条规模 | 常驻内存 |
| --- | --- | --- |
| 分类表 | 2000 个分类 | ~0.13 MB |
| 热分类数组（LRU 50 个 × 500 条 × 24B） | — | ~0.6 MB |
| 路径 arena（mmap，按页命中） | 70 MB 落盘 | 热页几十 MB，可回收 |
| 运行时/连接/缓存 | — | ~25–35 MB |
| **合计 RSS 目标** | | **60–90 MB**（含页缓存）<br>**堆 < 40 MB** |

对比：老结构 306 MB 堆，且随图片数线性涨。

## 访问路径（全部是「先查分类 → 再按需读该分类」）

| 接口 | 需要的数据 | 代价 |
| --- | --- | --- |
| `/json?cat` | 该分类数组 + arena | 2 次 mmap 读取 |
| `/img?category=x` | 该分类数组（分页） | 顺序读，可流式 |
| `/@img` | 分类表（含权重） → 选中分类的数组 | 1 次随机 + 1 次定位 |
| `/pic/...` | 只查「该文件是否存在」→ 直接出流 | 一次 hash 命中 |

没有任何路径需要遍历 100 万条。

## 自动方向（不能靠扫全量）

100 万张远端图不可能在索引期逐张解码。策略：**惰性判定 + 持久化**

1. 记录里 `ori` 2 bit：0=未知、1=横、2=竖、3=方
2. 任一图片被真正取用（出图或生成缩略图）时，顺手解析文件头（几十字节）→ 写回该 bit
3. 查询带方向时：`ori` 已知的按需过滤；未知的视为「可满足任意方向」，并优先被选中去判定
4. 热图很快全部判定完；冷图永远不判定，也就不花任何代价

## 本地 + 云端混合

分类表里每个分类带 `source`：

```
source = local  → /pic 走 sendfile（零拷贝）
source = remote → /pic 走「代理流式转发」（**不 302，不暴露后端地址**）
```

- 代理流式：`io.CopyN` 直通，32 KB 缓冲，内存与文件大小无关；支持 `Range`（视频拖动）
- 同一分类内可以混：本地有就本地出，没有就回源
- 热文件可选落「本地缓存盘」并设容量上限（LRU），冷文件永远不落盘
- 缩略图**必须**落本地（远端压不了），单独一个 LRU，建议 2–5 GB

## 不 302 之后，带宽怎么办

原图全部经源站转发，所以必须靠缓存摊销：

| 层 | 策略 |
| --- | --- |
| CDN | `/pic/...` 已有 `public, max-age=604800` + ETag → 7 天，命中后不回源 |
| 源站 | 可选本地热缓存（LRU），命中直接 sendfile |
| 未命中 | 代理流式转发（不落盘） |

实测口径：首次访问走一次远端，之后 7 天由 CDN 承接。

## 失败模式与对策

| 风险 | 对策 |
| --- | --- |
| 远端 LIST 100 万条很慢（分页 1000/页 = 1000 次请求） | 后台增量刷新：只拉「顶层目录的 mtime」，变了才重扫该子树 |
| 远端超时/限流 | 分类级熔断 + 指数退避；该分类降级为「暂不可用」，不影响其它分类 |
| 代理被打满 | 并发闸门（复用现有 memguard 压力模型）+ 每 IP 限速 |
| mmap 文件损坏 | 索引文件带 magic+版本+crC32，坏则整份重建（与快照同思路） |
| 冷启动 100 万条 LIST | 先出「分类骨架」，条目按需填充（渐进式可用，复用现有 progressive 逻辑） |

## 里程碑

| # | 内容 | 交付物 |
| --- | --- | --- |
| 1 | 紧凑索引（分类表 + 24B 记录 + arena + mmap） | `internal/index`，含 100 万条压测（内存/查询延迟） |
| 2 | store 切到新索引（本地目录源） | 行为不变，内存从 306 MB → <40 MB |
| 3 | remote 源（WebDAV/S3 listing → 分类表 + 条目） | 索引只存元数据，不落原图 |
| 4 | `/pic` 混合分流 + 代理流式（禁 302） | 本地 sendfile / 远端 io.Copy 直通 |
| 5 | 惰性方向判定 + 持久化 | `ori` 位回写，热图自动分类 |
| 6 | 缩略图 LRU（容量上限 + 冷热淘汰） | 磁盘可控 |

## 与当前实现的关系

- 现有 `store` 的**扫描/发布/快照/内存控制**逻辑保留，替换的是「内存里怎么放条目」
- `ECY_DATA_DIR` 语义扩展为「本地源」；新增 `ECY_REMOTE_*` 描述云端源
- 单机 100 万条时，目标 RSS 60–90 MB（含页缓存），堆 <40 MB
