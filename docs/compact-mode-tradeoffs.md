# compact 模式：舍弃了什么

> 100 万张实测：就绪 93ms、/json 22 288 QPS、峰值 130MB。这是拿什么换来的？

## 一、内存账（100 万张，实测）

| 项 | 体积 | 说明 |
| --- | --- | --- |
| 进程基线 | ~21 MB | Go 运行时 + 连接池 + 路由 |
| index.bin（mmap） | 37 MB | 可被内核回收，计入 RSS 但不占堆 |
| 位置数组缓存（1536 分类） | ~9 MB | 随机访问的位置索引 |
| dirs[].names | ~50 MB | 100 万个文件名字符串，增量扫描靠它比对 |
| 合计 | ~121 MB | 扫描收尾后实测值 |

想再降只能动 dirs[].names（见第三节）。

## 二、舍弃的语义（逐条对照）

| 能力 | 内存模式 | compact 模式 | 影响 |
| --- | --- | --- | --- |
| 条目本体 | 常驻堆 | 只在 mmap 里 | 这是收益来源 |
| 聚合桶 aggs | 预建，O(1) 取 | 按前缀现扫索引 | 父目录聚合每请求 O(分类数)，更慢但可用 |
| oriMeta 方向映射 | 每文件 126B | 不维护，方向存索引 | 依赖索引 size/mtime 校验，过期则重读文件头 |
| Verify() | 每次 stat | 直接信任索引 | 外部删除的文件要等下次扫描才 404（最长 10 分钟） |
| 增量扫描 | 文件名集合 diff | 同（names 仍保留） | 目前一致 |
| JSON 快照 | 有 | 不写 | 热启动只依赖 index.bin；索引丢了要全量重扫（159s） |
| 扫描期内存 | 常驻 | 临时全量 + 扫完释放 | 峰值 130MB，稳态 121MB |

## 三、还想再降：只能动 dirs[].names

它占 ~50MB，是「增量扫描按文件名 diff」的前提。丢掉它有两个代价：

1. 扫描退化为「按目录 mtime 判定 + 整目录重列」，目录没变就不动
2. 文件系统 mtime 粒度粗时可能漏掉一秒内的多次改动，需要周期性全量校验兜底

取舍：省 50MB，换「扫描更粗但有兜底」。默认不做，留给要求 <90MB 的场景。

## 四、选型建议

| 规模 | 建议 | 理由 |
| --- | --- | --- |
| ≤ 10 万张 | 内存模式 | 结构简单、语义完整、聚合最快 |
| 10 万–50 万 | 任一 | compact 已明显省内存，性能反超 |
| ≥ 50 万 | compact | 实测 100 万张 121MB / 22k QPS |

## 五、已知边界

- 单文件 >4GiB 时索引里的 size 会被 uint32 压平（尚未修）
- compact 模式的父目录聚合没有深度衰减，权重口径与内存模式略有差异
- /@img 与图库依赖「分类列表快照」，索引为空时会退化（已修：空结果不缓存）
