# 规模性能评估

> 所有数字来自单机实测（服务端与压测客户端同机），环境见文末。绝对 QPS 受这台机器的
> CPU 与「客户端同机争用」限制，**重点看趋势与成本结构**，不要直接当作线上容量。

## 结论

1. **读接口与数据规模解耦**：`/json` 的 QPS 在 100 张和 5 万张分类之间基本不变（18k→23k），
   因为随机取样是 O(limit)、按方向分桶在扫描期完成。
2. **成本随文件数线性增长的部分**：启动扫描（约 30 µs/文件）、内存（约 0.8 KB/文件）、
   节流重扫（约 1.2 µs/文件，每 3 秒一次）。
3. **唯一 O(n) 的用户可见路径是图库页**：单分类 1 万张 127 ms、5 万张 628 ms，
   生成的 HTML 也随图片数膨胀。这是当前最需要限制的规模瓶颈。
4. **冷缩略图是 CPU 密集型**：4K 图压到 480px 约 473 ms/张（≈2 张/秒/核）；
   缓存命中后 0.6 ms。冷缓存风暴会退化为回源原图（设计如此）。
5. **稳定性没问题**：24 秒 60 万请求、24.6k QPS、0 失败，RSS 稳定在 27 MB，句柄回落。

## 数据集规模（单分类、每张 64×36 PNG，横竖各半）

| 图片数 | 冷启动 | 启动后 RSS | 每 3 秒重扫* | `/json` QPS(c100) | 图库页 | 磁盘 |
| --- | --- | --- | --- | --- | --- | --- |
| 100 | 14 ms | 13.0 MB | 0.6 ms | 18.3k | 2.3 ms | 424 KB |
| 1,000 | 61 ms | 14.7 MB | 1.2 ms | 17.7k | 18 ms | 4 MB |
| 10,000 | 300 ms | 18.9 MB | 12 ms | 21.7k | 127 ms | 41 MB |
| 50,000 | 1,536 ms | 40.5 MB | 62 ms | 23.0k | **628 ms** | 197 MB |

* 「重扫」= 静置 3 秒后第一个请求的耗时，包含整个目录的 `ReadDir` + 条目名比对。
它发生在请求路径上（当前实现），所以是一次**每 3 秒一次的尾延迟尖峰**。

线性外推（仅供参考）：

| 规模 | 冷启动 | RSS | 重扫/3s | 图库页 |
| --- | --- | --- | --- | --- |
| 100k | ≈3 s | ≈80 MB | ≈120 ms | ≈1.2 s |
| 500k | ≈15 s | ≈400 MB | ≈600 ms | 不建议 |

## 并发（分类 1,000 张）

| 并发 | QPS | p50 | p99 |
| --- | --- | --- | --- |
| 10 | 15.2k | 0.51 ms | 3.5 ms |
| 100 | 20.5k | 3.7 ms | 18.9 ms |
| 500 | 19.9k | 18.0 ms | 88 ms |
| 1,000 | 19.4k | 40.6 ms | 111 ms |

QPS 在 c100 之后不再上升而延迟线性上涨 —— **客户端与服端同机，客户端先饱和**。
把服务端限到单核（`GOMAXPROCS=1`、c32）仍能跑到 **16.8k QPS**，说明单核处理能力接近实测上限，
真实上限需要独立客户端机器才能测准。

## 每请求 CPU 成本（服务端进程 CPU / 请求数）

| 路径 | CPU/请求 | 等效单核吞吐 |
| --- | --- | --- |
| `/json` 单条 | 81 µs | ≈12.3k req/s |
| `/json?cat=50` | 266 µs | ≈3.8k req/s |
| `/pic` 原图 | 138 µs | ≈7.2k req/s |
| `/pic?w=48` 缓存命中 | 148 µs | ≈6.8k req/s |

按 81 µs/请求、4 核估算，`/json` 单条的理论上限约 49k QPS（不含客户端开销）。

## 冷缓存与缩略图

| 场景 | 结果 |
| --- | --- |
| 4K PNG(1.7MB) → w=480，首次 | **473 ms** |
| 同上，缓存命中 | 0.6 ms |
| 4K 原图直出 | 1.1 ms |
| 200 张不同小图 × w=200，100 并发（全冷） | 1.11 s，200/200 成功，全部产出 webp |
| 同上，缓存就绪后 | 0.99 s（主要是 200 个 curl 进程开销） |

压缩队列容量 25：队列满时未命中缓存的请求**直接回退原图**（200 + `image/png`），
不会排队等 CPU。冷缓存风暴后建议用 CDN 预热或提前跑一遍 `?w=`。

## 多分类（200 个分类 × 250 张 = 5 万张）

| 指标 | 值 |
| --- | --- |
| 冷启动 | 1,361 ms |
| 启动后 RSS | 36.9 MB |
| 重扫首请求 | 39 ms |
| 图库页（单分类 250 张） | 8.3 ms |
| 后台首页（统计 200 个分类） | 6.1 ms |
| `/json` QPS(c100) | 20.6k |

同样是 5 万张，**拆成 200 个分类后图库页从 628 ms 降到 8 ms**——瓶颈是「单个分类的图片数」，不是总量。

## 稳定性（分类 10,000 张，c200 持续 24 秒）

| 时间 | RSS | 打开句柄 |
| --- | --- | --- |
| 起始 | 21.2 MB | 7 |
| 10 s | 28.1 MB | 296 |
| 30 s | 27.5 MB | 232 |
| 60 s（结束后） | 26.7 MB | 7 |

60 万请求、24.6k QPS、**0 失败**，内存与句柄都回到基线，无泄漏迹象。

## 建议（按收益排序）

1. **限制图库页**：单分类超过 ~1,000 张时只随机取 N 张（如 300）+ 提示「共 M 张」。
   可把 5 万张的 628 ms 压到 10 ms 级；这是唯一随规模恶化的用户路径。
2. **重扫移出请求路径**：把 `refreshIfStale` 改成后台协程定时扫描，
   消除「每 3 秒一次的尾延迟尖峰」（5 万张 62 ms、20 万张约 250 ms）。
3. **超大库（>100k）**：启动扫描与常驻内存线性增长，建议按分类拆分（如 `anime/2024` 多级目录），
   或把图片迁到对象存储 + 仅保留元数据。
4. **冷缩略图**：接 CDN 时提前预热常用宽度；或把容器 CPU 限额提到能覆盖
   `N 图 × 0.5 s / 目标预热时间`。

## 环境与复现

- 4 vCPU（Intel i5-5300U @2.3GHz）、3.8 GB 内存、Debian 12、Linux 6.12
- 压测期间同机还有其它构建任务，load average ≈2.1
- 服务端 `ECY_ACCESS_LOG=off`（否则日志格式化的开销会计入）
- 复现：

```bash
go build -o /tmp/ecyapi ./cmd/server
ECY_ADDR=127.0.0.1:8080 ECY_DATA_DIR=/path/to/categories ECY_ACCESS_LOG=off /tmp/ecyapi &
go run ./tools/loadgen 'http://127.0.0.1:8080/json?pc' 100 20000
```
