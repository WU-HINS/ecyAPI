# 多图库路径设计（主库不变 + 附加库 /2/、/3/…）

> 需求：主库行为与 URL 完全不变；额外目录在后台添加，挂到 `/2/`、`/3/`…；随机也按槽位隔离。

## URL 形状

| 功能 | 主库（现状不变） | 第 2 个库 | 第 3 个库 |
| --- | --- | --- | --- |
| 分类随机 | `/{分类}` | `/2/{分类}` | `/3/{分类}` |
| 图片 | `/pic/{分类}/{文件}` | `/2/pic/{分类}/{文件}` | `/3/pic/…` |
| JSON | `/json?{分类}` | `/2/json?{分类}` | `/3/json?…` |
| 图库 | `/img?category={分类}` | `/2/img?category=…` | `/3/img?…` |
| 全分类随机 | `/@img`（**仅主库**） | `/2/@img`（仅第 2 库） | `/3/@img` |
| 跨库随机 | — | 预留 `/@all`（跨所有库加权） | 同左 |

**决策点**：`/@img` 是否要包含附加库？建议**不包含**——
否则主库的随机分布会被新增目录稀释，用户会感觉「加入新库后主库抽到的图变少了」。
跨库需求用显式的 `/@all` 表达。

## 内部表示

```go
type Root struct {
    Slot uint8   // 0 = 主库（URL 无前缀），1 = /2/，2 = /3/ …
    Name string  // 后台显示名（可中文），仅用于管理界面
    Path string  // 真实目录
}

// 分类在内部统一带槽位前缀："\x00" 分隔，避免与真实目录名冲突
// 槽 0："风景/2024"          → 文件 system/<风景/2024>/x.jpg
// 槽 1："\x011/风景/2024"    → 文件 /mnt/b/风景/2024/x.jpg
```

用不可见分隔符而不是 `2/` 前缀，理由：真实分类名可能就叫 `2/xxx`，用可见前缀会撞。
URL 层再做映射（`/2/` ↔ `\x011/`），对外始终是干净的 `2`。

## 数据与配置

- `ECY_DATA_DIR`：主库，行为完全不变（不写槽位前缀）
- `data/roots.json`：附加库列表（与 `groups.json` 同风格），后台增删改
- 快照 / `index.bin`：分类名已带槽位前缀，格式无需改动

## 改动面

| 层 | 改动 |
| --- | --- |
| `config` | 新增 `Roots()`，主库来自 `ECY_DATA_DIR` |
| `store.scan` | 外层遍历 roots，`scanDir` 接收 base 路径与槽位前缀 |
| `store` 管理接口 | `absPath(cat, file)` 按槽位解析真实路径 |
| `server` 路由 | 识别 `/2/`、`/3/` 前缀 → 剥离后复用现有 handler，仅切换槽位过滤 |
| `server` 图库/JSON | 分类列表按槽位过滤（`Categories(slot)` / `Counts(slot)`） |
| 后台 | 「图库目录」页：添加/删除/启用，显示每个库的分类数与图片数 |

## 验收

1. 单库：所有 URL、`/@img` 分布与现在**逐字节一致**（用现有测试兜底）
2. 两库：`/2/pic/...` 能取到第 2 库的文件；主库 `/pic/...` 不受影响
3. `/@img` 只从主库抽；`/2/@img` 只从第 2 库抽
4. 两库存在同名分类（都叫 `风景`）时互不干扰
5. 后台删除第 2 库 → `/2/*` 全部 404，主库无影响

## 已知风险

- 槽位号一旦分配**不复用**（删了 /2 再添加应给 /4），否则旧链接会指向新库的另一张图
- `Verify` / 扫描要按根分别进行，某个根挂载失败（U 盘没插）不能让整个服务崩
- 缩略图缓存 key 需带槽位，否则两库同名分类会互相覆盖
